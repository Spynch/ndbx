# Документация проекта EventHub

## 1. Что это за проект

EventHub - это серверное приложение для работы с мероприятиями. В нем можно
создавать пользователей, входить в систему, создавать мероприятия, смотреть
списки мероприятий, ставить реакции, писать отзывы и получать рекомендации.

Проект сделан как учебная работа по базам данных. Главная идея проекта в том,
что разные виды данных хранятся в разных хранилищах:

- MongoDB хранит пользователей и мероприятия.
- Redis хранит сессии пользователей и временные готовые ответы.
- Cassandra хранит реакции и отзывы.
- Neo4j хранит связи между пользователями и мероприятиями для рекомендаций.

То есть это не просто приложение с одной базой. Здесь показано, как одно
приложение может использовать несколько хранилищ под разные задачи.

## 2. Что реализовано

В проекте реализован сервис мероприятий со следующими возможностями:

- проверка, что приложение работает;
- создание сессии для посетителя;
- регистрация пользователя;
- вход пользователя по имени и паролю;
- выход пользователя из системы;
- просмотр списка пользователей;
- просмотр одного пользователя;
- просмотр мероприятий конкретного пользователя;
- создание мероприятия;
- просмотр списка мероприятий;
- просмотр одного мероприятия;
- изменение некоторых данных мероприятия;
- лайки и дизлайки мероприятий;
- отзывы к мероприятиям;
- изменение своего отзыва;
- рекомендации мероприятий для пользователя.

Пользователь работает с приложением через веб-запросы. Ответы возвращаются в
формате JSON. Сессия хранится через cookie `X-Session-Id`.

## 3. Основные инструменты

В проекте используются такие инструменты:

- Python 3.12 - язык, на котором написано приложение.
- FastAPI - библиотека для обработки веб-запросов.
- Uvicorn - программа, которая запускает приложение как веб-сервер.
- Redis - быстрое хранилище для сессий и временных готовых данных.
- MongoDB - хранилище документов для пользователей и мероприятий.
- Cassandra - хранилище для реакций и отзывов.
- Neo4j - графовая база данных для построения рекомендаций.
- bcrypt - библиотека для безопасного хранения паролей.
- Docker Compose - запуск приложения и всех баз данных одной командой.
- Makefile - короткие команды для запуска и остановки проекта.

Также есть коллекция запросов для Postman в файле
`api/eventhub.postman_collection.json`. Ее можно использовать для ручной
проверки основных запросов.

## 5. Запуск проекта

Настройки лежат в `.env.local`. Там указаны порты, имена служб, названия баз,
время жизни сессий и другие параметры.

Основные команды:

```bash
make run
```

Запускает все службы в фоне.

```bash
make rund
```

Запускает все службы и показывает вывод в консоли.

```bash
make services
```

Показывает состояние контейнеров.

```bash
make stop
```

Останавливает контейнеры без удаления данных.

```bash
make clean
```

Останавливает контейнеры и удаляет сохраненные данные баз.

После запуска приложение доступно по адресу:

```text
http://localhost:8080
```

Порт берется из настройки `APP_PORT`.

## 6. Какие службы поднимаются

Через `docker-compose.yml` запускаются:

- `app` - само приложение на Python;
- `redis` - Redis для сессий и временных данных;
- `cassandra-test` - Cassandra;
- `cassandra-init` - одноразовая настройка Cassandra;
- `neo4j` - Neo4j;
- `neo4j-init` - одноразовая настройка Neo4j;
- `mongo-cfg-1`, `mongo-cfg-2`, `mongo-cfg-3` - узлы настроек MongoDB;
- `mongo-shard1-1`, `mongo-shard1-2`, `mongo-shard1-3` - первый набор узлов MongoDB;
- `mongo-shard2-1`, `mongo-shard2-2`, `mongo-shard2-3` - второй набор узлов MongoDB;
- `mongos` - точка входа в MongoDB;
- `mongo-init` - одноразовая настройка MongoDB.

Приложение стартует только после того, как основные базы данных стали готовы.
Это описано в `depends_on` в `docker-compose.yml`.

## 7. Как приложение запускается внутри

При запуске выполняется файл `app/main.py`.

Порядок такой:

1. Приложение читает настройки из переменных окружения.
2. Создает подключение к Redis.
3. Создает подключение к MongoDB.
4. Создает подключение к Neo4j.
5. При старте проверяет, что MongoDB отвечает.
6. Создает соединение с Cassandra и выбирает нужное пространство данных.
7. Проверяет соединение с Neo4j.
8. Если какая-то база еще не готова, приложение пробует подключиться повторно.

Количество попыток задается настройкой `APP_STARTUP_RETRY_ATTEMPTS`, а пауза
между попытками задается `APP_STARTUP_RETRY_DELAY_SECONDS`.

Когда приложение завершает работу, оно закрывает подключения к Redis, MongoDB,
Neo4j и Cassandra.

## 8. MongoDB

MongoDB используется для основных сущностей:

- пользователи;
- мероприятия.

База называется `eventhub`. Название задается настройкой `MONGODB_DATABASE`.

### Коллекция users

В коллекции `users` хранятся пользователи.

Основные поля:

- `_id` - внутренний номер MongoDB;
- `full_name` - полное имя;
- `username` - имя для входа;
- `password_hash` - сохраненный хеш пароля.

Пароль в открытом виде не хранится. При регистрации пароль превращается в хеш
через `bcrypt`, и уже этот хеш сохраняется в MongoDB.

Для `username` создан уникальный индекс. Это значит, что два пользователя с
одинаковым именем для входа создать нельзя.

### Коллекция events

В коллекции `events` хранятся мероприятия.

Основные поля:

- `_id` - внутренний номер MongoDB;
- `title` - название мероприятия;
- `category` - категория;
- `price` - цена;
- `description` - описание;
- `location.address` - адрес;
- `location.city` - город, если он задан;
- `created_at` - когда мероприятие создано;
- `created_by` - кто создал мероприятие;
- `started_at` - время начала;
- `finished_at` - время окончания.

В проекте MongoDB настроена как разделенная база. Коллекция `events`
разделяется по полю `created_by` с хешированием. Простыми словами, мероприятия
распределяются по разным узлам в зависимости от автора. Это нужно, чтобы
нагрузка могла распределяться между несколькими частями MongoDB.

Для поиска созданы индексы по названию, автору, категории, цене, городу и
дате начала.

## 9. Redis

Redis используется для быстрых данных, которые можно хранить временно.

В проекте Redis хранит:

- сессии пользователей;
- готовые подсчеты реакций;
- готовые подсчеты отзывов;
- готовые рекомендации.

### Сессии

Ключ сессии выглядит так:

```text
sid:<номер_сессии>
```

Внутри хранится:

- `created_at` - когда сессия создана;
- `updated_at` - когда сессия обновлена;
- `user_id` - номер пользователя, если пользователь вошел в систему.

Сессия имеет срок жизни. Он задается `APP_USER_SESSION_TTL`. При активных
запросах срок жизни продлевается.

### Временные данные реакций

Для реакций используется ключ:

```text
event:<хеш_названия>:reactions
```

Внутри лежат:

- `likes` - количество лайков;
- `dislikes` - количество дизлайков.

Название мероприятия превращается в md5-хеш. Это сделано, чтобы ключ Redis был
коротким и безопасным для хранения.

### Временные данные отзывов

Для отзывов используется ключ:

```text
event:<хеш_названия>:reviews
```

Внутри лежат:

- `count` - количество отзывов;
- `rating` - средняя оценка.

### Временные рекомендации

Для рекомендаций используется ключ:

```text
user:<номер_пользователя>:recomms
```

Внутри есть поле `events`, где лежит готовый список мероприятий.

## 10. Cassandra

Cassandra используется для данных, которые удобно хранить по ключам:

- реакции на мероприятия;
- отзывы на мероприятия.

Пространство данных задается настройкой `CASSANDRA_KEYSPACE`. В текущей
конфигурации это `testkeyspace`.

### Таблица event_reactions

Таблица хранит реакции пользователей.

Поля:

- `event_id` - номер мероприятия;
- `created_by` - номер пользователя;
- `like_value` - значение реакции;
- `created_at` - когда реакция записана.

Первичный ключ:

```text
(event_id, created_by)
```

Это значит, что один пользователь может иметь только одну текущую реакцию на
одно мероприятие. Если пользователь сначала поставил лайк, а потом дизлайк,
запись обновится.

Значения реакции:

- `1` - лайк;
- `-1` - дизлайк.

### Таблица event_reviews

Таблица хранит отзывы.

Поля:

- `event_id` - номер мероприятия;
- `created_by` - номер пользователя;
- `id` - номер отзыва;
- `rating` - оценка от 1 до 5;
- `comment` - текст отзыва;
- `created_at` - когда отзыв создан;
- `updated_at` - когда отзыв изменен.

Первичный ключ:

```text
(event_id, created_by)
```

Это значит, что один пользователь может оставить только один отзыв на одно
мероприятие. Потом он может этот отзыв изменить.

## 11. Neo4j

Neo4j используется для рекомендаций. Это графовая база данных, где удобно
хранить связи.

В графе есть два вида узлов:

- `User` - пользователь;
- `Event` - мероприятие.

У пользователя есть поле:

```text
id
```

У мероприятия есть поля:

```text
id
title
```

Связь между пользователем и мероприятием:

```text
(User)-[:LIKED]->(Event)
```

Такая связь создается, когда пользователь ставит лайк мероприятию.

В Neo4j создаются ограничения, чтобы `User.id` и `Event.id` были уникальными.
Также создается индекс по `Event.title`.

Важная особенность текущей реализации: при дизлайке связь `LIKED` из Neo4j не
удаляется. В Cassandra меняется текущая реакция, а граф продолжает хранить
факт, что пользователь когда-то проявлял интерес к мероприятию. Это влияет на
логику рекомендаций.

## 12. Пользователи и вход

### Регистрация

Запрос:

```text
POST /users
```

Нужно передать:

- `full_name`;
- `username`;
- `password`.

Логика работы:

1. Приложение проверяет, что все поля есть и они не пустые.
2. Пароль превращается в хеш через `bcrypt`.
3. Пользователь сохраняется в MongoDB.
4. В Neo4j создается узел `User`.
5. В Redis создается сессия.
6. В ответ ставится cookie `X-Session-Id`.

Если имя пользователя уже занято, возвращается ошибка `409`.

Если пользователь был сохранен в MongoDB, но Neo4j не ответил, приложение
пытается удалить пользователя из MongoDB. Так проект старается не оставлять
частично созданные данные.

### Вход

Запрос:

```text
POST /auth/login
```

Нужно передать:

- `username`;
- `password`.

Логика работы:

1. Приложение ищет пользователя в MongoDB по `username`.
2. Сравнивает переданный пароль с сохраненным хешем.
3. Если пароль верный, пользователь привязывается к текущей сессии.
4. Если сессии не было, создается новая.

При неверном имени или пароле возвращается `401`.

### Выход

Запрос:

```text
POST /auth/logout
```

Логика работы:

1. Приложение проверяет, что пользователь вошел в систему.
2. Удаляет сессию из Redis.
3. Отправляет cookie с нулевым временем жизни, чтобы браузер ее удалил.

## 13. Сессии

Сессия нужна, чтобы приложение понимало, какой пользователь делает запрос.

Создать пустую сессию можно запросом:

```text
POST /session
```

Если cookie сессии уже есть и сессия еще жива, приложение просто продлит ее
срок жизни и вернет `200`.

Если сессии нет, создается новая и возвращается `201`.

Проверка работы приложения:

```text
GET /health
```

Возвращает:

```json
{"status":"ok"}
```

Этот запрос не создает сессию. Если cookie уже была, он просто возвращает ее
обратно с обновленным временем жизни.

## 14. Мероприятия

### Создание мероприятия

Запрос:

```text
POST /events
```

Доступен только пользователю, который вошел в систему.

Нужно передать:

- `title` - название;
- `address` - адрес;
- `started_at` - время начала;
- `finished_at` - время окончания.

Можно передать:

- `description` - описание.

При создании приложение само ставит:

- `category` как `other`;
- `price` как `0`;
- `created_at` как текущее время;
- `created_by` как номер текущего пользователя.

Логика работы:

1. Проверяется сессия пользователя.
2. Проверяются обязательные поля.
3. Даты должны быть в формате RFC3339, например `2031-01-01T12:00:00+03:00`.
4. Мероприятие сохраняется в MongoDB.
5. В Neo4j создается узел `Event`.
6. Возвращается номер созданного мероприятия.

Если мероприятие сохранено в MongoDB, но Neo4j не ответил, приложение пытается
удалить мероприятие из MongoDB.

### Список мероприятий

Запрос:

```text
GET /events
```

Поддерживаются параметры:

- `title` - поиск по названию;
- `id` - поиск по номеру мероприятия;
- `category` - категория;
- `city` - город;
- `user` - имя пользователя, который создал мероприятие;
- `price_from` - цена от;
- `price_to` - цена до;
- `date_from` - дата начала от, формат `YYYYMMDD`;
- `date_to` - дата начала до, формат `YYYYMMDD`;
- `limit` - сколько записей вернуть;
- `offset` - сколько записей пропустить;
- `include=reactions` - добавить реакции;
- `include=reviews` - добавить сводку по отзывам.

Категории, которые принимает проект:

- `meetup`;
- `concert`;
- `exhibition`;
- `party`;
- `other`.

Если указать `include=reactions`, к каждому мероприятию добавится:

```json
{"likes":0,"dislikes":0}
```

Если указать `include=reviews`, к каждому мероприятию добавится:

```json
{"count":0,"rating":0.0}
```

Можно указывать оба значения:

```text
GET /events?include=reactions,reviews
```

### Просмотр одного мероприятия

Запрос:

```text
GET /events/{event_id}
```

Возвращает одно мероприятие. Также поддерживает `include=reactions` и
`include=reviews`.

### Изменение мероприятия

Запрос:

```text
PATCH /events/{event_id}
```

Доступен только автору мероприятия.

Можно изменить:

- `category`;
- `price`;
- `city`.

Если передать пустой `city`, поле города удаляется из мероприятия.

Название, описание, адрес и даты через этот запрос не меняются.

## 15. Реакции

Лайк:

```text
POST /events/{event_id}/like
```

Дизлайк:

```text
POST /events/{event_id}/dislike
```

Оба запроса доступны только пользователю, который вошел в систему.

Логика лайка:

1. Проверяется сессия.
2. Проверяется, что мероприятие существует в MongoDB.
3. В Neo4j создается связь `User -> LIKED -> Event`.
4. В Cassandra записывается реакция со значением `1`.
5. В Redis удаляется старый подсчет реакций по этому названию.
6. Новый подсчет реакций снова собирается из Cassandra и кладется в Redis.

Логика дизлайка:

1. Проверяется сессия.
2. Проверяется, что мероприятие существует в MongoDB.
3. В Cassandra записывается реакция со значением `-1`.
4. В Redis удаляется старый подсчет реакций по этому названию.
5. Новый подсчет реакций снова собирается из Cassandra и кладется в Redis.

Одна важная деталь: реакции считаются по названию мероприятия, а не только по
одному номеру. Если есть несколько мероприятий с одинаковым названием, то
сводка реакций собирается по всем таким мероприятиям.

## 16. Отзывы

Создать отзыв:

```text
POST /events/{event_id}/reviews
```

Получить отзывы мероприятия:

```text
GET /events/{event_id}/reviews
```

Изменить свой отзыв:

```text
PATCH /events/{event_id}/reviews/{review_id}
```

Правила:

- отзыв может создать только пользователь, который вошел в систему;
- один пользователь может оставить только один отзыв на одно мероприятие;
- оценка должна быть от 1 до 5;
- текст отзыва должен быть строкой длиной не больше 300 символов;
- изменить можно только свой отзыв.

При создании отзыва приложение использует условную вставку в Cassandra:

```text
IF NOT EXISTS
```

Это значит, что второй отзыв от того же пользователя к тому же мероприятию не
создастся. В таком случае вернется ошибка `409`.

Средняя оценка и количество отзывов считаются по всем мероприятиям с одинаковым
названием. Результат временно хранится в Redis.

## 17. Рекомендации

Запрос:

```text
GET /recommendations
```

Доступен только пользователю, который вошел в систему.

Логика рекомендаций такая:

1. Приложение проверяет пользователя по сессии.
2. Сначала ищет готовые рекомендации в Redis.
3. Если готовых рекомендаций нет, идет в Neo4j.
4. Neo4j ищет других пользователей, которые лайкали те же мероприятия.
5. Потом берутся другие мероприятия, которые лайкали эти похожие пользователи.
6. Мероприятия, которые текущий пользователь уже лайкал, исключаются.
7. По найденным номерам мероприятия загружаются из MongoDB.
8. Мероприятия с одинаковым названием объединяются.
9. Список сортируется и сохраняется в Redis.
10. Пользователь получает список мероприятий.

Сортировка работает так:

1. Сначала выше идут мероприятия с большим количеством лайков.
2. Если количество лайков одинаковое, выше идет более раннее мероприятие.
3. Если и дата совпадает, сортировка идет по названию.

Ответ имеет вид:

```json
{"events":[]}
```

Поля `count` в ответе рекомендаций нет.

## 18. Просмотр пользователей

Список пользователей:

```text
GET /users
```

Параметры:

- `name` - поиск по полному имени;
- `id` - поиск по номеру;
- `limit` - сколько вернуть;
- `offset` - сколько пропустить.

Просмотр одного пользователя:

```text
GET /users/{user_id}
```

Мероприятия пользователя:

```text
GET /users/{user_id}/events
```

Для мероприятий пользователя доступны почти те же параметры, что и для
`GET /events`: название, номер, категория, город, цена, дата, `limit`,
`offset`, `include=reactions`, `include=reviews`.

Пароль и хеш пароля в ответах по пользователям не возвращаются.

## 19. Проверки данных

В проекте есть простые проверки входных данных:

- строковые обязательные поля не должны быть пустыми;
- номера MongoDB должны быть правильными `ObjectId`;
- `limit`, `offset`, `price_from`, `price_to` должны быть целыми числами без минуса;
- дата для фильтра должна быть в формате `YYYYMMDD`;
- время мероприятия должно быть в формате RFC3339;
- категория должна входить в список разрешенных категорий;
- оценка отзыва должна быть от 1 до 5;
- текст отзыва должен быть не длиннее 300 символов.

Если поле неправильное, обычно возвращается:

```json
{"message":"invalid \"field\" field"}
```

где `field` - название поля.

## 20. Основные коды ответов

В проекте используются такие коды:

- `200` - запрос выполнен, данные возвращены;
- `201` - объект создан;
- `204` - запрос выполнен, тела ответа нет;
- `400` - неправильные данные в запросе;
- `401` - пользователь не вошел в систему или неверный пароль;
- `404` - объект не найден;
- `409` - конфликт, например пользователь или отзыв уже есть;
- `503` - одна из баз данных недоступна.

## 21. Как данные проходят через приложение

Пример полного сценария:

1. Посетитель вызывает `POST /session`.
2. Приложение создает сессию в Redis.
3. Посетитель вызывает `POST /users`.
4. Пользователь сохраняется в MongoDB.
5. В Neo4j создается узел пользователя.
6. Redis связывает сессию с этим пользователем.
7. Пользователь создает мероприятие через `POST /events`.
8. Мероприятие сохраняется в MongoDB.
9. В Neo4j создается узел мероприятия.
10. Другой пользователь ставит лайк.
11. Лайк записывается в Cassandra.
12. Связь лайка записывается в Neo4j.
13. Подсчет лайков временно сохраняется в Redis.
14. Когда пользователь открывает рекомендации, Neo4j ищет похожие интересы.
15. MongoDB отдает полные данные мероприятий.
16. Redis сохраняет готовый список рекомендаций на короткое время.

Так проект показывает, что каждое хранилище отвечает за свою часть задачи.

## 22. Зачем здесь несколько баз данных

MongoDB хорошо подходит для пользователей и мероприятий, потому что это
документы с разными полями. Мероприятие удобно хранить как один документ:
название, описание, место, даты, автор.

Redis подходит для сессий и временных готовых данных, потому что он быстрый и
умеет сам удалять ключи по истечении времени.

Cassandra подходит для реакций и отзывов, потому что эти данные удобно читать
по номеру мероприятия. Также там легко хранить одну запись на пару
`мероприятие - пользователь`.

Neo4j подходит для рекомендаций, потому что рекомендации строятся на связях:
какой пользователь какие мероприятия лайкал, и какие пользователи похожи по
интересам.

## 23. Краткий итог

Этот проект представляет сервис мероприятий. Пользователь может зарегистрироваться,
войти, создавать мероприятия, смотреть списки, ставить реакции, писать отзывы и
получать рекомендации. В проекте специально использованы разные базы данных:
MongoDB для основных документов, Redis для быстрых временных данных, Cassandra
для реакций и отзывов, Neo4j для связей и рекомендаций.

Проект хорошо показывает, как можно разделить данные по смыслу и выбрать для
каждой задачи подходящее хранилище.
